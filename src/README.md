# Jarvis Source Code Organization

Исходный код Jarvis организован по функциональным модулям:

## Структура директорий

```
src/
├── core/              # Основная орхестрация и точка входа
│   ├── orchestrator.py    # Главный движок Jarvis (диспетчеризация tool-вызовов)
│   ├── entry_point.py     # Vosk слушатель и голосовой ввод
│   ├── volition.py        # ProactiveGate: такт проактивной речи (тихие часы, анти-спам)
│   └── bootstrap.py       # Инициализация и запуск системы
│
├── inference/         # Слой инференса (Native Function Calling)
│   ├── openai_client.py   # Async HTTP-клиент к chat-серверу llama-server (:8080)
│   ├── embeddings.py      # Sync-клиент к embed-серверу (:8090) — замена Ollama
│   ├── agent.py           # Обобщённый агентный цикл tool-calling
│   ├── router.py          # Semantic Router: интент → категория + микро-промпт
│   ├── semantic.py        # L2: матч навыка по эмбеддингам (opt-in, калибруется)
│   ├── routing_stats.py   # Телеметрия лестницы: какой слой решил интент

│
├── skills/            # Каталог навыков (Skill Registry) — run_skill
│   ├── registry.py        # Ядро реестра: Skill, декоратор, enum, fuzzy-матч (L1b)
│   ├── ui_control.py      # KDE Plasma: приложения, звук, яркость, окна, медиа
│   ├── system_ops.py      # Диагностика: cpu/ram/disk/battery/network/…
│   ├── pentest.py         # Разведка: nmap-пресеты, порты, ARP
│   ├── screen.py          # «Глаза»: скриншот + OCR, активное окно, ошибки на экране
│   ├── patterns.py        # L1: шаблоны со слотами (громкость 30, скан 10.0.0.1)

│   ├── macros.py          # Макросы/сценарии: композиция навыков одной фразой
│   ├── healing.py         # SkillHealer: самолечение команд (варианты бинаря qdbus)

│
├── services/          # Фоновые сервисы и демоны
│   ├── daemon_swarm.py    # Наблюдатели системных событий
│   ├── recon_daemon.py    # Разведка сети и системы
│   ├── sentinel.py        # Безопасность и мониторинг
│   └── watch_service.py   # Глубокое наблюдение за событиями
│
├── memory/            # Управление памятью и состоянием
│   ├── engine.py          # Хранилище долгосрочной памяти (ChronoMemory, 3 слоя)
│   ├── storage.py         # Векторная база данных (Mnemosyne)
│   ├── reflection.py      # Ночная консолидация: недавняя память → core-факты
│   ├── ephemeral.py       # Эфемерный запуск кода в песочнице
│   └── snapshot.py        # Снимки состояния системы
│
├── ui/                # Пользовательский интерфейс
│   ├── hud.py             # HUD и визуализация (PyQt6; Wayland layer-shell)
│   ├── window_manager.py   # Управление окнами KWin
│   └── pixel_renderer.py   # Рендеринг пикселей для дисплея
│
├── audio/             # Обработка аудио
│   ├── audio_engine.py    # Кинематографический голосовой тракт (Piper + SoX)
│   ├── segmentation.py    # Резка реплики на предложения для streaming TTS (opt-in)
│   ├── wakeword.py        # Wake-word пред-гейт перед Vosk (opt-in, openWakeWord)
│   └── fft_analyzer.py    # FFT анализ PCM для сферы HUD
│
├── network/           # Сетевые утилиты
│   └── scanner.py         # Сканирование сети (nmap-стриминг на визор)

│   └── execution.py       # Shadow execution и sandboxing
│
└── common/            # Общие утилиты
    ├── event_bus.py       # Шина событий
    ├── parser.py          # Очистка/санитизация bash для gated-fallback
    ├── singleton.py       # Singleton паттерн
    └── repair.py          # Быстрое исправление ошибок (QuickPatcher)
```

## Архитектура команд: Skill Registry (`src/skills/`)

Нейросеть **не пишет bash на лету**. Она переводит речь оператора в строгий
`skill_id` из заранее написанного, протестированного каталога навыков, а Python
исполняет заведомо рабочую функцию:

1. `IntentRouter` (regex/embedding) классифицирует интент в категорию и отдаёт
   короткий микро-промпт + каталог навыков категории.
2. Модель вызывает `run_skill(skill_id, reply, …)` — `skill_id` ограничен
   grammar-enum по каталогу, так что несуществующий навык невозможен.
3. Оркестратор озвучивает `reply` и запускает хендлер навыка (выверенный
   `qdbus6`/`wpctl`/`brightnessctl`/…). Разрушительные навыки (`destructive=True`)
   проходят голосовое подтверждение.

`execute_bash` остаётся **gated-fallback** для длинного хвоста: уходит в
ShadowExec (песочница) и heal-цикл — редкий резерв, а не горячий путь.

### Макросы/сценарии: композиция навыков одной фразой

Над каталогом одиночных навыков стоит слой **сценариев** (`skills/macros.py`):
именованная последовательность навыков под одну команду — «рабочее место
пентеста» (терминал + IP + слушающие порты), «режим фокуса» (тёплый экран +
тишина), «доложи обстановку» (cpu + память + диск). Матч точный по фразе (как
alias fast-path), исполнение детерминировано: ядро (`_try_macro`) гонит шаги
через тот же `_invoke_skill`, собирает телеметрию speaks_result-шагов в один
устный брифинг. Разрушительные шаги пропускаются (макросы их и не содержат —
двойная защита). Проверяется в `process_intent` перед alias fast-path: сценарий
выше одиночного навыка.

### Лестница распознавания: речь → навык за минимум усилий

Цель — обращаться к тяжёлой и порой ошибающейся 3B как можно **реже**. Поэтому
`process_intent` пропускает фразу через ступени от самой дешёвой и строгой к
самой дорогой; первая, что уверенно сработала, — побеждает, остальные не
запускаются. Все ступени детерминированы (никакого LLM), разрушительные навыки
на любой из них проходят голосовое подтверждение.

| Ступень | Что ловит | Как | Стоимость |
|---------|-----------|-----|-----------|
| **L0 alias** | точную фразу-алиас («терминал», «тише») | `skills.match_alias` — обратный индекс по нормализованной фразе (регистр/пробелы/ё·е/пунктуация) | микросекунды |
| **L0 macro** | точную фразу-сценарий («режим фокуса») | `macros.match_macro` — композиция навыков; выше одиночного навыка | микросекунды |
| **L1 pattern** | команду со **слотом** («громкость 30», «быстрый скан 10.0.0.1») | `patterns.match` — regex с именованными группами = args навыка; числительные словами → цифры | микросекунды |
| **L1a app-resolver** | «открой/запусти **X**» | regex глагола + `apps.resolve` (синонимы → fuzzy); имя резолвится в **захардкоженную** команду каталога, а не в shell | микросекунды |
| **L1b fuzzy** | дрейф Vosk («терминэл») | `skills.fuzzy_match_alias` / `macros.fuzzy_match_macro` — difflib с порогом + зазором; разрушительные исключены | микросекунды |
| **L2 semantic** | парафраз без строкового сходства («хочу выйти в интернет» → браузер) | `semantic.SemanticSkillMatcher` — косинус эмбеддингов к per-skill экземплярам; **opt-in, требует калибровки** | HTTP+CPU, ~десятки мс |
| **L3 model** | всё остальное: разговор, сложное извлечение, неоднозначность | `IntentRouter` → микро-промпт + 3B (native tool-calling) | секунды |

Каждая ступень — отдельный `_try_*`-метод; их общий хвост (`_run_fastpath_skill`)
единообразно гейтит разрушительные, озвучивает и пишет в память/диалог. L1/L1a/L1b
покрывают **голову** частотного распределения команд детерминированно; L2 — opt-in
мост для парафраза; L3 остаётся для настоящего хвоста.

**Телеметрия лестницы** (`inference/routing_stats.py`): `process_intent`
возвращает тег-результат, ядро маппит его в уровень (L0…L3) и периодически
логирует долю **разгрузки 3B** (сколько интентов решено без модели) и разбивку
по слоям. Это и есть обратная связь «куда добавлять алиасы и окупается ли L2».

## Self-authoring: навыки, которые Джарвис пишет себе сам

Длинный хвост решается без ручного труда. Когда `execute_bash`-fallback успешно
(rc=0, не разрушительно) исполняет одну и ту же команду `PROMOTE_THRESHOLD` раз,
`SkillLearner` (`skills/learning.py`) предлагает оператору закрепить её навыком.
На голосовое «да» команда пишется в `config/learned_skills.json`, и **горячая
перезагрузка** (FileChangeWatcher следит за `config/`) поднимает процесс со
свежим кодом, где `skills/learned.py` уже зарегистрировал навык.

Безопасность: учится только ФИКСИРОВАННАЯ команда, уже прошедшая ShadowExec и
гейты при первых запусках (повтор не даёт новых прав); разрушительное и `sudo`
не учатся никогда; промоушен только по явному «да». Счётчики использования живут
в `jarvis_memory/` (не под наблюдением watcher'а), чтобы обучение не дёргало
перезагрузку само по себе.

## Самолечение навыков (автоматический «# VERIFY on target»)

Боль: встроенный навык систематически падает, потому что имя DBus-бинаря/
интерфейса различается между версиями Plasma (`qdbus6` vs `qdbus` vs
`qdbus-qt6`). Раньше это правилось руками — отсюда метки `# VERIFY on target` в
навыках. Теперь `_SkillCtx.run` чинит сам (`skills/healing.py` → `SkillHealer`):

1. команда навыка упала (rc≠0);
2. healer выдаёт **детерминированных** кандидатов-замен (варианты бинаря qdbus —
   никакого LLM на горячем пути);
3. первый кандидат с rc=0 — это и есть «VERIFY на целевой машине», только
   автоматический; рабочую замену запоминаем в `jarvis_memory/skill_overrides.json`
   (per-host, НЕ под наблюдением watcher'а), и впредь навык сразу идёт по ней.

Безопасно: подменяется лишь имя известного семейства бинарей, а гарантия —
реальный rc=0; разрушительные навыки и так гейтятся подтверждением ДО запуска.
Самопочинка озвучивается («переключил qdbus6 на qdbus и закрепил») — это и есть
наблюдаемое подтверждение оператору. Если выученная замена однажды перестанет
работать (обновили Plasma), healer её забывает и лечит заново.

## Память, которая взрослеет (reflection)

Раз в сутки в простое `memory/reflection.py` перечитывает события последних
суток (warm+lite слои) и просит модель выделить УСТОЙЧИВЫЕ факты об операторе
(предпочтения, привычки, имена, проекты). Извлечённое уходит в **core-слой**
(не истекает по TTL) с дедупом против уже известного. Через недели Джарвис
по-настоящему знает оператора, а не отвечает с чистого листа.

## Глаза на экране (screen perception)

`skills/screen.py` даёт дешёвые «глаза»: скриншот (grim/spectacle/scrot) → OCR
(`tesseract rus+eng`) + заголовок активного окна. Работают фразы «что на экране»,
«прочитай ошибку», «какое окно активно». Без VLM — на N100 этого достаточно для
чтения диалогов, ошибок и содержимого окон.

**Проактивный взгляд** (`orchestrator._screen_watch_loop`): глаза, связанные с
волей. В простое (тот же `ProactiveGate` — тихие часы, анти-спам) Джарвис изредка
смотрит, не появился ли на экране **новый стек-трейс/ошибка**, и сам предлагает
помощь («Сэр, вижу на экране ошибку … Подсказать?»). Бережно к N100 и приватности:
сначала дешёвый пред-фильтр по заголовку окна (`looks_like_dev_context` —
терминал/редактор/IDE), и только тогда дорогой OCR; повторы давит дедуп гейта; в
память кладётся лишь факт инициативы, не текст экрана. Отключается одним env:
`JARVIS_SCREEN_WATCH=0`.

Порог тишины (и проактивной речи, и взгляда) по умолчанию 1200с (20 минут).
Для проверки на железе его незачем выжидать — опусти через
`JARVIS_PROACTIVE_INTERVAL` (секунды), напр. `JARVIS_PROACTIVE_INTERVAL=60
jarvis run`. `jarvis test` показывает текущий порог и помечает тестовый режим.

## Эмбеддинги без Ollama (суверенная память)

Векторы памяти (ChronoMemory) считает не демон Ollama, а **второй лёгкий
`llama-server --embedding`** на порту 8090 с маленькой **мультиязычной** моделью
(`src/inference/embeddings.py` → `EmbeddingClient`; Chroma-обёртка
`LlamaServerEmbedding` в `memory/engine.py`). Это убирает целый рантайм и точку
отказа: один стек llama.cpp на всё, out-of-process (Python весов не держит),
эмбеддер крошечный (~120M) и крутится на **CPU** — iGPU остаётся под 3B-мозг.
Весь батч уходит одним HTTP-запросом в OpenAI-совместимый `/v1/embeddings`. Код
модель-агностичен; модель/порт настраиваются через `JARVIS_EMBED_MODEL` /
`JARVIS_EMBED_ENDPOINT`. Поднять: `./setup_embed_server.sh` (юнит
`jarvis-embed.service`). Sentinel реникает под нагрузкой именно embed-инстанс
(по cmdline-маркеру `--embedding`), не трогая chat-сервер.

> Смена embedding-модели меняет размерность вектора → старая база
> `./jarvis_memory` несовместима. При миграции/смене модели:
> `rm -rf ./jarvis_memory`.

## Эхо-гейт: Джарвис не слышит сам себя

`entry_point.py` глушит вход микрофона, пока работает голос, иначе Vosk
распознаёт собственную речь Джарвиса и само-триггерится. Гейт закрывается по
`STATE_CHANGE=SPEAKING` и продлевается на каждый звуковой `AUDIO_FFT`-фрейм
(~раз в 23 мс); открывается не по `IDLE` (его шлёт и оркестратор — порядок
событий не гарантирован), а по истечении короткого «хвоста» после последнего
звукового фрейма. Пока гейт закрыт, поток дренируется, но в распознаватель не
подаётся; на выходе из гейта рекогнайзер сбрасывается (`Reset`), чтобы не
выдать мусорный partial. Аудио-стек (sounddevice/vosk) импортируется мягко —
без него модуль работает в standby, а логика гейта остаётся тестируемой.

## Буфер диалога: связный контекст последних реплик

Оркестратор держит последние `DIALOGUE_TURNS` пар (оператор → Джарвис) и
подаёт их в `build_context` отдельной секцией `[Dialogue]` вплотную к интенту —
чтобы 3B разрешала ссылки («закрой его», «то же для второго»). Это дополняет, а
не заменяет RAG-recall: recall — про давнее и семантическое, буфер — про
«здесь и сейчас». Бюджет токенов на N100 жёсткий, поэтому реплики обрезаются, а
в буфер пишутся только полные пары (пустой ввод/немой ответ не засоряют контекст).

## Измеримость роутера (eval harness)

`tests/eval_dataset.py` + `tests/router_eval.py` — golden-набор «фраза →
категория» и счётчик точности/recall. CLI-отчёт: `python scripts/eval_router.py`.
Гоняй на каждое изменение лексикона роутера или каталога — видно, стало лучше
или хуже, а не на глаз. Регресс-порог стережёт `tests/test_router_eval.py`.

## Соглашения по именованию

- **Модули**: snake_case (`orchestrator.py`, `window_manager.py`)
- **Классы**: PascalCase (`JarvisMain`, `DaemonSwarm`, `KWinOrchestrator`)
- **Функции**: snake_case (`compute_bands()`, `stream_nmap()`)
- **Константы**: UPPER_CASE (`LLAMA_MODEL_PATH`, `WEAVER_MEMORY_FACTS`)

## Импорты

После реорганизации все импорты используют полные пути:

```python
# Правильно ✓
from src.core.orchestrator import Jarvis
from src.common.event_bus import EventBus, EventType
from src.memory.engine import ChronoMemory

# Неправильно ✗ (больше не работает)
from core import Jarvis
from event_bus import EventBus
```

## Как запустить

Единая точка входа `./jarvis` (из корня репо) делает всё одной командой и
локализована на русском:

```bash
./jarvis setup      # поставить/докачать ВСЁ, чего нет (пакеты, venv, сборка,
                    # модели, systemd-юниты, глобальный симлинк ~/.local/bin/jarvis)
./jarvis test       # сквозная диагностика без изменений: компоненты, оба сервера,
                    # GPU-оффлоад, память, голос, инструменты — с вердиктом ✓/⚠/✗
./jarvis run        # лёгкая авто-починка + поднять оба сервера + ассистент (foreground)
./jarvis help       # список всех команд (status/stop/logs/restart/wipe-memory)
```

Ниже — те же шаги вручную, если нужен тонкий контроль:

```bash
# Сервер инференса (один раз): chat-мозг + embed-сервер памяти (вместо Ollama)
./setup_server.sh            # llama-server :8080 (Qwen2.5-3B, Vulkan/iGPU)
./setup_embed_server.sh      # llama-server :8090 (--embedding, мультиязычный, CPU)

# Бессмертный запуск (рекомендуется): внешний супервизор стережёт Джарвиса
python -m src.core.supervisor            # демонизируется, переживает закрытие терминала
python -m src.core.supervisor status     # жив ли супервизор и bootstrap
python -m src.core.supervisor restart    # перезапустить bootstrap немедленно
python -m src.core.supervisor stop        # единственный способ корректно остановить всё

# Прямой запуск без супервизора (для отладки)
python -m src.core.bootstrap

# Запуск тестов
pytest tests/ -v

# Линтинг
ruff check .
```

## Производительность на N100: env-тумблеры (Tier 0)

Базовый мозг по умолчанию — **Qwen2.5-3B-Instruct** (тот же footprint Q4_K_M,
сильнее в русском и tool-calling; сменить — `MODEL_NAME`/`MODEL_URL`/`MODEL_ALIAS`
у `setup_server.sh`, плюс `JARVIS_LLM_MODEL` у клиента — алиас обязан совпадать).
Остальные ускорения **выключены по умолчанию** — включать осознанно и измерять,
память N100 (8 ГБ shared) — связывающее ограничение.

| Env | Что делает | Где | Замечания |
|-----|------------|-----|-----------|
| `JARVIS_LLM_KV_QUANT=q8_0` | KV-quant + flash-attn: вдвое режет KV-кэш, ускоряет декод | `setup_server.sh` (пере-`setup`) | Vulkan-FA версионно-капризна; strip-safety снимет, если сборка не тянет |
| `JARVIS_LLM_DRAFT=1` | Speculative decoding (draft Qwen2.5-0.5B предсказывает за 3B) | `setup_server.sh` | На 8 ГБ впритык по RAM — мерить tok/s; качает draft-GGUF |
| `JARVIS_STREAM_TTS=1` | Streaming TTS: реплика по предложениям, первое слово раньше | рантайм (`audio_engine`) | стык между piper-процессами; OFF = байт-в-байт прежнее |
| `JARVIS_WAKEWORD=1` | Wake-word пред-гейт перед Vosk: меньше нагрев/ложные | рантайм (`entry_point`) | нужен `pip install openwakeword`; без него — fail-open (не блокирует) |
| `JARVIS_SEMANTIC_MATCH=1` | L2: матч навыка по эмбеддингам (парафраз без 3B) | рантайм (`orchestrator`) | **сначала** `python scripts/calibrate_semantic.py` → выставить `JARVIS_SEMANTIC_THRESHOLD` |

Калибровка порога L2 (зависит от embedding-модели): `scripts/calibrate_semantic.py`
гоняет golden-набор через живой embed-сервер и рекомендует порог с максимумом
recall при нуле опасных матчей. Wake-word окно/порог — `JARVIS_WAKEWORD_WINDOW`/
`JARVIS_WAKEWORD_THRESHOLD`.

## Бессмертие и горячая перезагрузка

Джарвис спроектирован как **самовосстанавливающаяся** сущность — двумя слоями:

**Слой 1 — горячая перезагрузка кода (`src/core/immortal.py`).**
Внутри процесса bootstrap живёт `FileChangeWatcher`: следит за `src/` и
`config/`. Как только вы отредактировали файл или сделали `git pull`, процесс
делает `os.execv` и поднимается со **свежим кодом и тем же PID** — все изменения
подхватываются автоматически, вручную перезапускать ничего не нужно. Сервер
инференса llama-cpp живёт в отдельном процессе, поэтому при перезагрузке кода
модель остаётся «тёплой» в RAM.

> Почему `os.execv`, а не `importlib.reload`? Живое Qt+asyncio+потоки-приложение
> после `importlib.reload` остаётся в полусломанном состоянии (слоты и синглтоны
> держат ссылки на старые классы). `os.execv` даёт честный чистый старт нового
> кода без потери дескрипторов — это и есть «корректно подхватить все изменения».

**Слой 2 — внешний супервизор (`src/core/supervisor.py`).**
Демон, который стережёт `python -m src.core.bootstrap` и поднимает его при
**любом** завершении: краш, OOM-килл, `kill`, Ctrl+C. Сам супервизор при старте
делает double-fork и `setsid`, поэтому закрытие терминала его не убивает.
Именно поэтому **остановка `python -m src.core.bootstrap` не убивает Джарвиса** —
супервизор за ~секунду поднимает его обратно. Падения получают экспоненциальный
backoff (1→2→4→…→30с), плановая перезагрузка кода — мгновенный подъём.

**Продакшн — systemd (`config/jarvis.service`).**
`ExecStart` запускает супервизор в foreground, `Restart=always` + `WatchdogSec=30`
ловят даже зависший event-loop. Установка: `scripts/install_service.sh`.

## HUD — живая сущность, строго зафиксированная (`src/ui/hud.py`)

- **Позиция намертво зафиксирована.** Рамка по периметру + круглое «пятно» в
  правом нижнем углу (ratio `0.88, 0.86`) НИКОГДА не съезжают: запросы на
  репозицию (`set_core_position`) игнорируются, периодический «дрейф» по
  квадрантам убран — остался только pin поверх окон (KWin под Wayland иначе
  сбрасывает флаги keepAbove/skipTaskbar).
- **Рамка дышит в такт голосу.** В состоянии `SPEAKING` цвет и альфа рамки
  лерпуются `dim → peak` по уровню голоса (`FFT level`), конкурирующие
  QPropertyAnimation глушатся, чтобы пульсом владел только звук.
- **Пятно — индикатор речи с нулевой задержкой.** Круглая сфера в углу видна
  ТОЛЬКО когда Джарвис реально произносит звук (`state == SPEAKING` и
  `fft_level > 0.05`); в тишине её нет. Радиус и яркость пульсируют по `FFT
  level`. Энергия берётся из `PiperFFTPump` (~100 Hz) прямо из PCM-потока перед
  `aplay`, с back-pressure от звуковой карты — поэтому пульс совпадает с голосом
  практически без задержки. HUD перерисовывается 30 fps, чисто на QPainter
  (никакого GL — он валил Intel N100).

## Голос Джарвиса (TTS post-processing)

Синтез речи: **Piper** (`piper/ru_RU-dmitry-medium.onnx`) → raw PCM →
цепочка эффектов **sox** → `aplay`. Тракт вынесен в
`src/audio/audio_engine.py` (`AcousticEngine`); DSP-цепочки по состоянию —
в `_DSP_CHAINS`.

Цель DSP — приблизить нейтральный TTS к **кино-Джарвису** (Пол Беттани):
тёплый гладкий британский баритон, ровная подача, лёгкая «хай-фай»-комната.
Сознательно **без** фейзера и «шиммера» на верхах — они звучат робото-/сай-фай,
прочь от оригинала. Профили по состоянию:

| Профиль         | Когда                                  | Характер                          |
|-----------------|----------------------------------------|-----------------------------------|
| `normal`        | обычный ответ                          | тёплый баритон, тонкая комната    |
| `idle`          | IDLE state                             | глубже, медленнее, просторнее     |
| `alert`         | ALERT / destructive gate               | сухой, собранный, «впереди»       |
| `night_stealth` | темно (Pixel-сенсор) или ≥23ч / ≤6ч    | тёмный, тёплый, тихий             |

**Потолок метода (важно):** sox формирует тембр/стиль/пространство, но НЕ
переносит саму идентичность голоса актёра — спикер под капотом остаётся
русский мужской Piper. Для точного клонирования тембра Беттани нужен слой
**voice conversion** (RVC / so-vits-svc), обученный на сэмплах JARVIS, между
Piper и sox. Параметры цепочки можно валидировать на синтетическом тоне:

```bash
sox -n -t raw -r 22050 -e signed -b 16 -c 1 /tmp/t.raw synth 1 sine 130 sine 260
sox -t raw -r 22050 -e signed -b 16 -c 1 /tmp/t.raw -d <эффекты-профиля>
```

> Примечание: при частоте 22050 Гц частота Найквиста = 11025 Гц, поэтому
> shelf/eq выше ~11 кГц бессмысленны (теплота строится на низах и гладкости).
